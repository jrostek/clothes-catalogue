# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Layout

npm-workspaces monorepo (`apps/*`, `libs/*`) with Nx on top: the `@nx/jest` plugin infers `test`, and every other target (`lint`, `typecheck`, …) comes from the package scripts. TypeScript project references (backend, dtos) are wired from the root `tsconfig.json`; shared compiler options live in `tsconfig.base.json`. The frontend is not a reference, since Expo's tsconfig isn't composite.

**Toolchain.** TypeScript `~7.0.2` (the native Go compiler) is a single root devDependency; it ships only the `tsc` binary, no legacy JS API, so tools that load TypeScript as a library (typescript-eslint, ts-jest, ts-node) are not used. Linting is oxlint + oxlint-tsgolint (type-aware rules on TypeScript 7), configured by the root `.oxlintrc.json` that each project's `.oxlintrc.json` extends. Prettier is the formatter. `@nestjs/cli` 11 depends on its own TypeScript 5.9.3, which npm hoists to `apps/backend/node_modules/typescript` — so a bare `tsc`/`npx tsc` inside `apps/backend` runs 5.9.3. The backend `typecheck` script calls the root TypeScript 7 binary by path for that reason; nothing in the build uses 5.9.3. `apps/backend/tools/aspire-apphost` is a separate npm project with its own lockfile, not a workspace — run `npm install` there too.

- `apps/backend` — NestJS 11 API (`@clothes-catalogue/backend`), Swagger UI at `/swagger`, listens on `PORT` (default 3000).
- `apps/backend/tools/aspire-apphost` — Aspire TypeScript AppHost that orchestrates the local dev stack.
- `apps/frontend` — Expo 57 / React Native app (`@clothes-catalogue/frontend`) using expo-router (file-based routes in `src/app/`).
- `libs/dtos` — `@clothes-catalogue/dtos`, request/response types shared between backend and frontend.

## Commands

Install once from the repo root: `npm install`. Across all projects: `npx nx run-many -t typecheck lint test`.

### Backend (`apps/backend`)

The unprefixed scripts (`start`, `dev`, `build`, `lint`, `format`) do **not** run Nest — they delegate to the Aspire AppHost. The plain Nest scripts carry a `nest:` prefix.

| Goal | Command (run in `apps/backend`) |
|---|---|
| Full local stack (Postgres + Redis + backend) via Aspire | `npm run dev` (needs the `aspire` CLI; runs `aspire run`) |
| Nest only, watch mode | `npm run nest:start:dev` |
| Build Nest (SWC, no typecheck) | `npm run nest:build` |
| Typecheck (`tsc -b`, TypeScript 7) | `npm run typecheck` |
| Lint Nest sources (oxlint, auto-fixes) | `npm run nest:lint` |
| Check formatting (Prettier) | `npm run nest:format:check` |
| Lint the AppHost | `npm run lint` |
| Create + apply a migration after editing the schema (needs `DATABASE_URL`) | `npm run prisma:migrate:dev -- --name <change>` |
| Regenerate Prisma Client | `npm run prisma:generate` |
| Browse the database | `npm run prisma:studio` |
| Unit tests | `npm test` |
| Single test file | `npx jest path/to/file.spec.ts` or `npx jest -t "test name"` |

Nest compiles with its SWC builder (`nest-cli.json`: `builder.type: "swc"`, `typeCheck: false`; decorator metadata is kept on in `.swcrc`, which Nest DI needs), so `nest build`/`nest start` never report type errors — run `npm run typecheck`. Jest 30 config lives inline in `apps/backend/package.json` (`rootDir: src`, `*.spec.ts`, transformed by `@swc/jest`). There are no e2e tests.

`npm run dev` needs Docker and a value for the secret parameter `sqlPassword`: set it once with `aspire secret set Parameters:sqlPassword <value>` in `tools/aspire-apphost`, or pass `Parameters__sqlPassword` as an env var. The Postgres container and its data volume are persistent, so the password must stay the same across runs.

### Frontend (`apps/frontend`)

`npm start` (Expo dev server), `npm run web` / `android` / `ios`, `npm run lint` (oxlint with react, react-hooks, jsx-a11y and import plugins), `npm run typecheck` (`tsc --noEmit`). From the root: `npm -w @clothes-catalogue/frontend run <script>`. Metro compiles with Babel, so TypeScript 7 only affects typechecking. In VS Code, use the TypeScript 7 native language service (see `apps/frontend/.vscode/extensions.json`).

React is pinned twice: in `apps/frontend/package.json` and in the root `overrides` (which keeps npm from hoisting a second, newer React for Expo's peer dependencies). Bump both together, and use `npx expo install --fix` to keep Expo SDK packages on the patch versions the installed SDK expects.

## Architecture notes

- **Aspire orchestration.** `apphost.mts` provisions a persistent Postgres container (database `clothes-catalogue`, user `asia`, secret parameter `sqlPassword`) and Redis (`cache`), then launches the backend with `addJavaScriptApp('backend', '../..', { runScriptName: 'nest:start' })` — i.e. it runs `npm run nest:start` in `apps/backend`, injecting connection info for `db` and `cache` as env vars. The imported `./.aspire/modules/aspire.mjs` is generated by the Aspire CLI and gitignored; it appears after the first `aspire run` (or `aspire restore`), and the AppHost `typecheck`/`build` fail on a fresh clone until then. Aspire hosting package versions are pinned in `aspire.config.json`.
- **Persistence (Prisma 7).** Models live in `apps/backend/prisma/schema.prisma`, migrations in `prisma/migrations/`, and CLI settings in `prisma.config.ts` (the datasource URL comes from `DATABASE_URL`; the schema's `datasource` block has no `url` in Prisma 7). The `prisma-client` generator writes a CommonJS client (`moduleFormat = "cjs"`, extensionless imports so Jest resolves it) to `src/generated/prisma`, which is gitignored and excluded from oxlint, Prettier and coverage. It is regenerated by the backend `postinstall` and after `prisma:migrate:dev`; Prisma 7 no longer does either on its own. Inject `PrismaService` (`src/services/prisma.service.ts`, a `PrismaClient` using the `@prisma/adapter-pg` driver adapter) wherever you need the database. In Aspire, the AppHost passes the database URI as `DATABASE_URL` and runs a `db-migrations` resource (`npm run prisma:migrate:deploy`) that the backend waits for, so pending migrations are applied on every `npm run dev`. Postgres is published on the fixed host port 5432, so CLI commands outside Aspire can use `apps/backend/.env` (see `.env.example`). `DatabaseController` exposes test endpoints for the connection: `GET /database/health` (latency, server version, applied migrations; 503 when unreachable) and `GET`/`POST /database/probes` over the `ConnectionProbe` test table. Redis is provisioned but not used by the backend yet.
- **Shared DTOs are type-only.** `libs/dtos` exports raw `.ts` (`"exports": { ".": "./index.ts" }`) with no build step, and DTOs are plain `type`s imported via `import type`. They therefore produce no runtime metadata, so Nest validation pipes and `@nestjs/swagger` cannot introspect them (and the Swagger CLI plugin needs the TypeScript compiler API, which TypeScript 7 does not ship). Add new DTOs under `libs/dtos/<feature>/` and re-export them from `libs/dtos/index.ts`. For Swagger, the backend mirrors each DTO it uses in a controller as a class under `apps/backend/src/dtos/<feature>/` with the same name: the class `implements` the shared type (so drift is a compile error) and carries `@ApiProperty()` decorators. Controllers import these classes as values (not `import type`) for `@Body()` parameters, and reference them in `@ApiOkResponse`/`@ApiCreatedResponse` for response schemas.
- **Logging.** The backend logs through `nestjs-pino` (JSON to stdout, one `request completed` entry per HTTP request). `src/instrumentation.ts` is the first import in `main.ts` and starts the OpenTelemetry `NodeSDK` with the http, express, nestjs-core and pino instrumentations: requests become traces, and every pino record is exported as an OTLP log (with its request's trace id) to the Aspire dashboard's Structured logs. The SDK reads only the `OTEL_*` env vars that Aspire injects; it stays off when `OTEL_EXPORTER_OTLP_ENDPOINT` is unset (e.g. `nest:start:dev`). Log with Nest's `Logger` from `@nestjs/common` as usual.
- **Backend structure.** Controllers live in `src/controllers/`, services in `src/services/`, all registered in the single `AppModule`.
- **Frontend.** Path alias `@/*` → `src/*`. Platform-specific variants use the `.web.tsx` / `.web.ts` suffix next to the native file (e.g. `app-tabs.tsx` vs `app-tabs.web.tsx`). Typed routes and the React Compiler are enabled in `app.json`.
